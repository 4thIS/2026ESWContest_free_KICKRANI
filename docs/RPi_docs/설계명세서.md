## 0. 변경 배경 & 설계 원칙

기존 **ESP32(수집부) + 라즈베리파이(구동·추론)** 분리 구조를, ESP 업로드 난항·통신 복잡도·도메인 갭 제거를 위해
**라즈베리파이 하나로 통합**한다. Pi가 4가지를 담당: **① RC카 구동 ② 속도제어 ③ 데이터 수집 ④ 앱 통신**.

**★ 설계 원칙 — 독립 개발 후 통합**
- 4가지는 **각각 독립 서브시스템**으로 개발한다(한 번에 만들지 않는다).
- 서로는 **계약(인터페이스)만** 알고, 내부 구현은 모른다 → 각자 따로 만들고·테스트하고, 마지막에 **통합 계층**이 조립.
- 통합 순서: 각 서브시스템 단독 완성 → 계약대로 연결.
- 기존 ESP 코드(`collector/`)는 `archive/collector-esp/`로 보존.

## 1. 시스템 컨텍스트

| 항목 | 선정 |
| --- | --- |
| 컴퓨트 | **Raspberry Pi 5** |
| 언어/런타임 | **Python** |
| 진동 센서 | MPU-6050 (I2C, 하드웨어 FIFO) |
| 속도 센서 | 엔코더/홀센서 (GPIO 인터럽트) |

| 앱 통신 | **BLE** (Pi = GATT 서버) |
| 학습 | **PC(오프라인)** — Pi는 추론만 |

## 2. 공통 계약 (모든 서브시스템의 접점)

먼저 **이 계약들을 고정**해야 각자 독립 개발이 가능하다.

**자료형**
```python
Sample = { "t_ms": int, "ax","ay","az": int, "gx","gy","gz": int, "wheel_pulse": int }
RoadClass = "asphalt" | "bike_path" | "sidewalk_block" | "concrete" | "gravel"
Mode = "IDLE" | "COLLECT" | "DEMO"
```

**샘플 스트림**: `③ 데이터수집`이 `sample_queue`(Sample 스트림)를 생산 → 수집(로거)·인지가 소비.

**앱 명령/텔레메트리(④ 계약)**
- 명령(앱→Pi): `SET_MODE {collect|demo}` · `START` · `STOP` · `SET_LABEL <name>`
- 텔레메트리(Pi→앱): `{ state, mode, road_class, speed, recording_file }`

# 서브시스템 명세 (각각 독립 개발)

각 절: **목적 / 인터페이스(계약) / 입출력 / 의존 / 단독 테스트 / 담당**

## ① RC카 구동 (drive)  · `pi/motion/motor.py`

- **목적**: 모터에 PWM 듀티 출력. 직진/정지만(조향 없음).
- **인터페이스**
  ```python
  class Motor:
      def set_duty(self, duty: float): ...   # 0.0~1.0, 직진 속도
      def stop(self): ...                    # 즉시 정지(안전)
  ```
- **입력**: duty 명령 → **출력**: TB6612 GPIO PWM
- **의존**: GPIO(`gpiozero`+`lgpio`) — 다른 서브시스템 의존 없음
- **단독 테스트**: 듀티 주면 바퀴 회전, `stop()` 즉시 정지 (바퀴 공중)
- **담당**: 동제 (dj)

## ② 속도제어 (speed control)  · `pi/motion/speed_controller.py`

- **목적**: 목표 속도를 유지/도달. 엔코더 피드백으로 듀티 조정.
- **인터페이스**
  ```python
  class SpeedController:
      def set_target(self, speed): ...   # 목표 속도(또는 목표 듀티)
      def update(self): ...              # 주기 호출: 엔코더 읽어 Motor 듀티 보정
      def stop(self): ...
  ```
- **입력**: 목표속도 + 엔코더 속도 → **출력**: ①`Motor.set_duty()` 호출
- **의존**: **①(Motor)**, 엔코더(③의 센서 or 공유 엔코더 드라이버)
- **단독 테스트**: 목표속도 주면 바퀴가 그 속도로 수렴(엔코더 로그 확인)
- **담당**: 동제 (dj)
- ※ 1차는 오픈루프(고정 듀티 테이블)로 시작 → 필요 시 PID 피드백.

## ③ 데이터 수집 (data collection)  · `pi/sensors/` + `pi/collect/`

- **목적**: IMU+엔코더를 200Hz로 샘플링해 `sample_queue` 생산, 수집모드에선 CSV 저장.
- **인터페이스**
  ```python
  class Sampler:                 # sensors/sampler.py (스레드)
      def start(self): ...       # FIFO drain+엔코더 → sample_queue
      def stop(self): ...
  class Logger:                  # collect/logger.py
      def open(self, label: str): ...
      def write(self, s: Sample): ...
      def close(self): ...
  ```
- **입력**: 센서(MPU FIFO, 엔코더) → **출력**: `sample_queue` + `run_XXXX.csv`
- **의존**: MPU(`smbus2`), 엔코더(GPIO). 다른 서브시스템 의존 없음.
- **단독 테스트**: 정지 시 az≈1g, **실측 200Hz**, CSV 행수≈시간×200·gap 없음
- **담당**: 찬우 (cw)
- **CSV 스키마**: `timestamp_ms, ax, ay, az, gx, gy, gz, wheel_pulse`

## ④ 앱 통신 (app comm)  · `pi/comm/ble_server.py`

- **목적**: BLE GATT 서버. 앱 명령 수신 + 텔레메트리 송신.
- **인터페이스**
  ```python
  class BleServer:
      def on_command(self, cb): ...      # cb(command_dict) 등록
      def send_telemetry(self, data): ...# {state,mode,road_class,speed,file}
      def start(self): ...               # 광고 시작
  ```
- **입력**: 앱 명령 → **출력**: `command_queue`(또는 콜백) + 앱에 notify
- **의존**: `bluezero`(BlueZ). 다른 서브시스템 의존 없음(계약만).
- **단독 테스트**: 폰으로 연결→명령 로그 찍힘, 더미 텔레메트리 notify 표시
- **담당**: 찬우 (cw) — Pi측 BLE 서버 (스마트폰 앱 자체는 도현/`app`)

## (공유) 노면 인지 (perception/inference)  · `pi/infer/` + `pi/policy.py`

> ③의 샘플 스트림을 받아 ②의 목표속도를 만드는 **두뇌**. 4서브시스템을 잇는 핵심이라 별도 명시.

- **목적**: 샘플 → 윈도우 → 노면 분류 → 목표속도.
- **인터페이스**
  ```python
  class Windower: def add(self, s: Sample) -> Window | None: ...
  class Model:    def predict(self, w: Window) -> RoadClass: ...
  def policy(road: RoadClass) -> target_speed: ...
  ```
- **의존**: ③의 `Sample` 계약(스트림). 하드웨어 비의존.
- **단독 테스트**: 저장된 CSV로 **오프라인 예측**, mock 윈도우로 로직 검증
- **담당**: 찬우 (cw) — 학습은 PC, 추론만 Pi(TFLite).

# 통합 계층

## 3. 통합 계층 (controller)  · `pi/controller.py` + `pi/main.py`

위 5개를 **모드에 따라 연결**하는 얇은 오케스트레이터. 각 서브시스템의 **인터페이스만** 호출(내부 모름).

```
COLLECT:  ③Sampler → ③Logger(CSV)        ;  ②SpeedController=순항 → ①Motor
DEMO:     ③Sampler → 인지(Windower→Model→policy) → ②SpeedController → ①Motor
          Controller → ④BleServer.send_telemetry(노면·속도)
④ 명령(SET_MODE/START/STOP) → Controller 상태 전이
```

- Controller는 각 파트를 **주입(의존성 주입)** 받아 조립 → 파트 교체·mock 쉬움.
- 각 서브시스템이 **먼저 단독 완성**되어 있으면, 통합은 "계약대로 배선"만.

## 4. 동시성 모델

**단일 프로세스, 3 스레드 + 2 큐**
- **Sampler 스레드**(③): FIFO drain(HW 200Hz) → `sample_queue` (지터는 FIFO가 흡수)
- **Controller 스레드**: `sample_queue` 소비 → 모드별 라우팅, `②.update()` 주기 호출, telemetry 갱신
- **BLE 스레드**(④): 명령 in / 텔레메트리 out
- 공유: `sample_queue`(③→Controller), `command_queue`(④→Controller), `telemetry`(Controller→④, lock)
- **motor는 ②/Controller 경로만** 조작(단일 writer). GIL은 C 백엔드(I2C·TFLite·PWM)라 무해(Pi 5).

## 5. 모드 & 상태머신

`INIT → IDLE ↔ COLLECT / DEMO` (+ SAFE)

| 현재 | 트리거 | 동작 | 다음 |
| --- | --- | --- | --- |
| INIT | init 완료 | ④ 광고 시작 | IDLE |
| IDLE | `SET_MODE` | 모드 선택 저장 | IDLE |
| IDLE | `START`(collect) | ③Logger.open, ②순항 | COLLECT |
| IDLE | `START`(demo) | ②순항 | DEMO |
| COLLECT | `STOP` | ③Logger.close, ①stop | IDLE |
| DEMO | `STOP` | ①stop | IDLE |
| COLLECT/DEMO | **BLE 끊김/에러** | **즉시 ①stop**+(수집이면 파일보존) | IDLE(SAFE) |

**시작 시퀀스**(`main.py`): config → ③센서 init → ①모터 init(**정지 확정**) → 인지 모델 로드 → ③Sampler 스레드 → ④광고 → **IDLE**.

## 6. 에러 처리 & 안전 (공통)

**대원칙: 불확실하면 느리게/정지. 모터 기본상태 = 정지.**

| 실패 | 감지 | 대응 |
| --- | --- | --- |
| IMU 초기화 실패 | WHO_AM_I | IDLE 유지·보고 |
| IMU 읽기 에러 | I2C 예외 | 재시도→SAFE(①stop) |
| FIFO 오버플로 | 플래그 | FIFO 리셋+gap 로그 |
| 엔코더 무펄스 | 일정시간 0 | 속도0 취급·경고 |
| 디스크 풀/쓰기실패 | 예외·사전체크 | 녹화중단·파일닫기·보고 |
| 모델 로드 실패 | 파일없음 | DEMO 비활성(COLLECT 가능) |
| 추론 예외/저신뢰 | 예외·confidence↓ | 윈도우 스킵→기본 감속 |
| BLE 끊김 | 연결 이벤트 | **즉시 ①stop**+광고 재개 |
| 제어 예외 | try/except | 듀티0·GPIO LOW·SAFE |

- **워치독(필수)**: Controller 주기 kick, Sampler 사망/정지 >500ms → 워치독이 ①stop.
- **데이터 무결성**: 버퍼링 write + 1초 fsync(손실 ≤1초), 1주행=1파일, 비정상 종료에도 flush·close.
- **자원 정리**: signal(SIGTERM/SIGINT)·atexit → ①stop→파일close→GPIO정리→④정지.

## 7. 데이터 & ML 규격

- **200Hz 근거**: 노면 고주파 정보(자갈길 등)를 담으려면 나이퀴스트상 대역폭×2. DLPF 94Hz로 안티에일리어싱.
- **윈도우**: 1차 시간(0.5~1초)+속도 feature → 2차 거리(1~2m 리샘플). 비교 실험 = 보고서 어필.
- **학습/추론 분리**: 학습 PC(세션단위 train/test 분리, 혼동행렬), 추론만 Pi(TFLite).
- **노면 5종**: 아스팔트·자전거도로(안전) / 보도블럭·콘크리트(주의) / 자갈길(위험).

## 8. 하드웨어 / 배선 (Pi 5) — 4WD · L298N 확정 (2026-07-27, DJ)

> 구동: **4WD, L298N 2채널**(좌=ENA→OUT1/2 / 우=ENB→OUT3/4). **직진 전용**.
> 속도센서: **A3144 홀센서 + 자석 확정** (광엔코더 폐기).
> 핀 단일 출처: `RPi/pi/config.py`.
> ⚠️ **공통 자산 변경** — 드라이버·전원 반영은 전원 담당(찬우)에게 **통지·합의 후** main 머지. 모터 4개 기준 전류·전원(벅컨버터/배터리) 재계산 필요.

| 서브시스템 | 신호 | Pi 5 핀(BCM) | 인터페이스 |
| --- | --- | --- | --- |
| ③ MPU-6050 | SDA / SCL | GPIO2 / GPIO3 | I2C-1 (AD0=GND → 0x68) |
| ③/② A3144 홀센서 | 펄스(DO) | GPIO17 | GPIO 인터럽트(풀업) · DO–VCC 10kΩ |
| ① L298N 좌(ENA) | 속도 PWM | GPIO18 | HW PWM |
| ① L298N 우(ENB) | 속도 PWM | GPIO13 | HW PWM |
| ① L298N IN1~IN4 | 방향(고정) | — | 보드에서 +5V/GND 고정(전진) |
| 공통 | GND | GND | 공통 접지 |

- **직진 전용**: IN1·IN3=+5V, IN2·IN4=GND로 **하드웨어 고정**(전진). Pi는 방향 GPIO를 안 쓰고 속도(ENA·ENB PWM)만 제어. 정지=ENA/ENB PWM 0.
- ⚠️ L298N **ENA·ENB 점퍼캡 제거**해야 PWM 동작(안 빼면 최고속 고정).
- 홀센서 개방컬렉터 → **DO–VCC 10kΩ 풀업** 필수. 바퀴/축 자석, PPR=자석 수 → `ENCODER_PULSES_PER_REV` 실측 보정.
- L298N 전압강하 ~2V(모터가 배터리보다 약하게 돔)·발열 → 방열판. Pi 전원은 L298N 5V(0.5A) 금지, **별도 벅컨버터**.
- ⚠️ **모터·Pi 전원 격리**(별도 배터리/디커플링, +12V에 470~1000µF) — 안 하면 Pi 리셋.

## 9. 개발 순서 (독립 → 통합)

1. **① 구동** 단독 (바퀴 공중, 듀티·정지 확인)
2. **③ 데이터 수집** 단독 (200Hz·CSV·gap 없음)
3. **④ 앱 통신** 단독 (폰↔더미 명령·텔레메트리)
4. **② 속도제어** (①+엔코더 결합, 목표속도 수렴)
5. **인지** (③의 CSV로 오프라인 학습·예측)
6. **통합 계층** (계약대로 배선 → 모드 동작)

각 단계는 서로 **병렬 진행 가능**(계약 고정 덕분).
